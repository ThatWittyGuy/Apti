### Q14. How did you track milestones and deliverables at Gagangiri Foods?

**Model Answer:**

**S:** The Gagangiri Foods project had a roughly 3.5-month timeline with several technical milestones — from data collection through model training, evaluation, dashboard development, and final delivery. Without a tracking system, it would have been easy for tasks to drift unnoticed.

### Q15. What challenges did you face during the Gagangiri Foods project and how did you handle them?

**Model Answer:**

**S:** One of the most significant challenges was data availability. The AI/ML model needed labeled microscopy images of water samples — some with microplastics, some without — to train on. This data had to come from the company's own laboratory samples because generic public datasets of this specificity didn't exist.

**T:** I needed to manage this as a project dependency and ensure we had enough quality training data to meet the accuracy target without delaying the project.

**A:** I flagged data collection as a critical dependency early, before it became a blocker. I worked with the company's lab team to understand their capacity — how many samples they could prepare per week, what the labeling process looked like, and who was responsible.

I created a data intake tracker — logging batch number, date received, number of samples, labeling status, and integration into the training pipeline. This gave visibility to both the lab team and the AI/ML team.

When we hit a point where we needed more diverse samples (samples from different water conditions to improve model robustness), I raised this with the business stakeholder with clear context: 'Our current accuracy is 73.5% and we've identified that the model is not seeing enough variation in turbidity conditions. We need 50 additional samples from the secondary water source to reach the 80% target.' This specificity helped the stakeholder act quickly.

**R:** We ultimately collected sufficient data to train a model achieving 80.9% accuracy — exceeding our minimum threshold of 80%. The parallel workstream approach saved approximately 2–3 weeks of potential idle time."

### Q16. How did you apply PM skills to an AI/ML project specifically?

**Model Answer:**

"AI/ML projects have unique PM challenges compared to traditional software development, and I learned this firsthand at Gagangiri Foods.

The three biggest differences I observed were:

**First, data as a dependency.** In traditional software, the team controls its inputs. In ML, you're dependent on data quality and quantity that often comes from outside the team. I treated data collection as a first-class project dependency — building it into the tracker, assigning clear ownership, and monitoring it weekly the same way I'd monitor a development task.

**Second, experimental, non-linear progress.** Traditional software has a clear linear SDLC. ML model development is iterative and uncertain — a model might hit 73% accuracy and then plateau. The team spent two iterations trying different approaches before Transfer Learning got us to 80.9%. As a PM, I had to manage stakeholder expectations around this uncertainty — framing it as 'we are in iteration X and here is what we've learned' rather than 'we are behind schedule.'

**Third, evaluation metrics as deliverable milestones.** In software, 'done' usually means the feature works. In ML, 'done' means the model meets a defined accuracy/precision/recall threshold. I incorporated these metric targets into our milestone tracker as acceptance criteria — so a model 'milestone' wasn't 'model trained' but 'model achieves ≥80% binary classification accuracy on the validation set.'"

### Q22. What is a REST API and why does it matter for project tracking?

**Model Answer:**

"A REST API is a set of rules for how two software systems communicate over the internet using standard HTTP methods — GET to retrieve data, POST to create it, PUT or PATCH to update it, and DELETE to remove it. In a modern web or mobile application, the frontend (what users see) talks to the backend (server-side logic) through API calls.

I built and consumed REST APIs at Globant — for example, building an authentication endpoint that accepted user credentials via POST, validated them against the database, and returned a JWT token for session management.

Why this matters for project tracking: APIs are almost always dependencies between teams. The frontend team cannot build a feature until the backend API for it exists. When I'm tracking a sprint and a frontend story shows 'blocked,' the first question I'd ask is 'is the API ready?' If the API delivery slips, the frontend timeline slips too. Understanding this lets me catch API dependency risks early and surface them to the team before they become sprint-ending blockers."

### Q23. You mentioned optimizing SQL queries and reducing API response times by 30–40%. How does performance optimization work in a PM context?

**Model Answer:**

**S:** At Globant, I was tasked with investigating why certain dashboard API endpoints were loading slowly — users were experiencing 4–6 second load times on pages that should have been near-instant.

**T:** I needed to diagnose the root cause and implement a fix.

**A:** I used database query analysis tools to examine the execution plans of the slow queries. I identified two main issues: first, several queries were using multiple unindexed JOINs across large tables, causing full table scans instead of indexed lookups. Second, some queries were pulling far more data than the frontend actually needed — no pagination, no field selection.

I added composite indexes on the most frequently joined columns, rewrote specific queries to use more efficient JOIN strategies and SELECT only needed fields, and added pagination for large result sets.

**R:** Response times dropped from 4–6 seconds to under 1 second — a 30–40% improvement in API response time, and practically a much larger improvement from the user's perspective.

**PM Relevance:** This experience taught me how performance problems get discovered, diagnosed, and fixed — and how long it takes. When a stakeholder says 'the dashboard is slow, can we fix it this sprint?' I know to ask: has the root cause been identified? Is it a query issue, a server issue, a network issue? ### Q28. Tell me about a technical problem you solved and what the PM lesson was.

### Q38. Walk me through the Scrum ceremonies. Have you participated in any?

**Model Answer:**

"Scrum has five key ceremonies that structure how a team plans, executes, and continuously improves.

**Sprint Planning** happens at the start of each sprint — typically 2 weeks. The Product Owner presents the highest-priority backlog items, and the team selects what they can commit to completing. Stories are broken into tasks and estimated. Output: a committed sprint backlog.

**Daily Stand-up** is a 15-minute daily sync where each person answers: what did I do yesterday, what will I do today, is anything blocking me? It's the team talking to each other — not a status report to a manager.

**Sprint Review** happens at sprint end. The team demos completed work to stakeholders, collects feedback, and updates the backlog accordingly. It's focused on the product output.

**Sprint Retrospective** also happens at sprint end, but focuses on the team process — what went well, what didn't, what we'll change. Only the Scrum team attends — no external stakeholders.

**Backlog Refinement** is ongoing mid-sprint — the team and PO clarify, estimate, and prioritize upcoming backlog items to prepare them for future sprint planning.

At Globant, I participated in team standups and sprint reviews within the software development team. I understand what these look like from the developer side — and I'm eager to now contribute from the coordination side, preparing agendas, documenting outcomes, and tracking action items."

### Q39. What is the difference between a Product Backlog and a Sprint Backlog?

**Model Answer:**

"The Product Backlog is the master, prioritized list of all work for the product — features, bug fixes, technical debt items, enhancements. It's owned by the Product Owner and continuously updated. It's never 'done' — as long as the product exists, the backlog evolves. Think of it as the full wishlist for the product.

The Sprint Backlog is the subset of Product Backlog items the team commits to completing in a specific sprint. It's created during Sprint Planning and owned by the Development Team. Once a sprint starts, the Sprint Backlog ideally doesn't change — it represents the team's commitment for that time-box.

**Analogy:** The Product Backlog is your grocery list for the whole month. The Sprint Backlog is what you're buying this weekend — a planned, committed subset of the full list.

At Gagangiri Foods, I maintained something functionally equivalent to this — a full project task list (our 'product backlog') and a 'this month' working list (our sprint equivalent) that we pulled from based on phase of the project."

### Q40. What is a user story and how do you write a good one?

**Model Answer:**

"A user story is a short, user-centered description of a feature written from the perspective of who will use it and what value it gives them.

The format: **As a [user type], I want [to do something], so that [I get this benefit].**

Example: 'As a food safety officer, I want to see a daily water quality status on the dashboard, so that I can quickly identify whether production can proceed safely without running a manual lab test.'

A good user story has several qualities:

**It's specific about the user type** — not just 'user' but 'food safety officer' or 'admin' or 'new visitor.' Different users have different needs.

**The goal is concrete** — not 'manage my account' but 'update my email address and receive a confirmation.'

**The benefit is meaningful** — it explains the 'why,' which guides design decisions. If the benefit is unclear, the feature might be built in a way that doesn't actually serve the user.

**It has acceptance criteria** — the Definition of Done for this specific story. Written as Given/When/Then:
- Given I am logged in as a food safety officer
- When I open the dashboard
- Then I see today's water quality status as Green, Amber, or Red based on the latest AI analysis

**It's appropriately sized** — a story should fit within a sprint. If it's too big, it becomes an Epic and needs to be broken down.

From my PM work at Gagangiri, I was effectively writing requirement statements in this style — translating stakeholder needs into specific, testable deliverables for the technical team."

### Q41. What is the SDLC and what phase is most important?

**Model Answer:**

"The Software Development Life Cycle is the structured process for planning, creating, testing, and deploying software. The standard phases are: Requirements, System Design, Implementation (Coding), Testing (QA), Deployment, and Maintenance.

Each phase has clear inputs, outputs, and stakeholders. Requirements feeds into Design, Design feeds into Implementation, and so on — though in Agile, these phases happen iteratively within each sprint rather than sequentially.

As for the most important phase — I'd argue **Requirements** is the most consequential, because errors made here compound through every subsequent phase. A feature built to the wrong requirement will be tested thoroughly, deployed correctly, and delivered wrong. The later you catch a requirements error, the more expensive it is to fix.

The old software engineering principle applies: a bug found in requirements costs $1 to fix. The same bug found in production costs $100.

This is why I prioritize requirements gathering and documentation in my PM work — at Gagangiri Foods, the requirements document I created was referenced repeatedly throughout the project to resolve scope questions. It paid dividends every time."

### Q42. What is a sprint burndown chart and how do you use it for tracking?

**Model Answer:**

"A sprint burndown chart is a visual representation of work remaining versus time remaining in a sprint. The X-axis is the sprint timeline (days 1 through 10 for a 2-week sprint), the Y-axis is remaining story points (or tasks). There's an 'ideal burndown' line — a straight line from the total sprint points on Day 1 to zero on Day 10. The actual burndown is plotted as work gets completed.

Patterns I'd look for as a PM tracking a sprint:

**Flat line** — the actual line isn't going down. Work isn't being completed. This means the team is blocked, stories are larger than estimated, or there's a quality issue causing rework. I'd raise this in standup immediately.

**Cliff at the end** — everything gets done in the last 2 days. This suggests the team was working but not marking things as 'Done' — possibly because items were waiting for code review or QA sign-off. This is a process issue to raise in the retrospective.

**Under the ideal line** — the team is burning faster than expected. Capacity to pull additional items from the backlog.

**Sharp drops, then flat** — items completed in batches but gaps in between. Possible integration or dependency issue mid-sprint.

I would review the burndown chart daily — it takes 30 seconds and gives an immediate health check on sprint progress. At Gagangiri, I used a simplified version of this: tracking task completion rates against our weekly milestone targets."

### Q43. What is the difference between velocity and capacity in Agile?

**Model Answer:**

"**Velocity** is a historical metric — how many story points a team actually completed in past sprints. It's calculated by averaging completed points over the last 3–5 sprints. If a team has averaged 32 points per sprint over the last four sprints, their velocity is 32.

**Capacity** is a forward-looking calculation — how many story point's worth of work can this team realistically do in the upcoming sprint, given who is available? If two team members are on vacation, capacity drops. If the team just grew by one person, capacity goes up.

Velocity tells you what the team has done. Capacity tells you what they can likely do next sprint.

In sprint planning, you use both: 'Our velocity is 32 points, but two people are out next sprint, so our adjusted capacity is about 22 points. Let's plan to pull 20–22 points to stay conservative.'

Why this matters for PM tracking: If a team's velocity suddenly drops — say from 32 to 18 — that's a signal. Was there a mid-sprint addition? More bugs than expected? Team conflict? Understanding the cause helps the PM support the team and reset stakeholder expectations on delivery timelines."

### Q44. How would you handle scope creep in a sprint?

**Model Answer:**

"Scope creep is one of the most common causes of missed sprint goals, and it often happens gradually — one 'small' addition here, one 'quick fix' there.

My approach has three components:

**Prevention — clear sprint commitment:** At sprint planning, the sprint backlog is agreed upon. Any addition post-planning should go through a deliberate process, not a casual Slack message. I'd advocate for a written rule: if it's not in the sprint backlog, it doesn't happen this sprint without an explicit change.

**Detection — daily monitoring:** In standup and on the board, I'd watch for tasks that appeared without being in the original sprint backlog. If I see a new Jira ticket assigned mid-sprint that wasn't planned, I'd ask: what is this, why is it in this sprint, and what is it displacing?

**Response — trade-off conversation:** If something genuinely urgent must be added mid-sprint, that's a legitimate trade-off — but it should be made explicitly. 'If we add this P0 bug fix to the sprint (estimated 3 points), we need to remove one 3-point story from the sprint backlog. What should come out?' This conversation with the PO and PM makes the cost visible rather than invisible.

At Gagangiri, I had a real scope creep moment when the technical team wanted to expand the model to classify microplastic types. I caught it early, framed it as a scope decision, and got stakeholder alignment to defer it — protecting the delivery timeline."

### Q45. What is Kanban and when would you use it instead of Scrum?

**Model Answer:**

"Kanban is a visual, flow-based Agile framework. Work is visualized on a board with columns representing stages (To Do, In Progress, In Review, Done), and teams limit Work in Progress (WIP) to ensure focus and reduce bottlenecks. Unlike Scrum, there are no sprints, no fixed ceremonies, and no prescribed roles.

I would recommend Kanban over Scrum in these scenarios:

**Continuous flow work** — support queues, bug fix teams, and operations teams that have a constant stream of incoming work without defined project cycles benefit more from Kanban. You can't plan a 2-week sprint when new support tickets arrive hourly.

**Teams new to Agile** — Kanban's lower overhead (fewer ceremonies, no velocity tracking initially) can be a gentler entry point.

**Maintenance phases** — after a major product launch, the team shifts from feature development to bug fixes and minor enhancements. Kanban is a natural fit here.

For an AI product team in active feature development — building sprints of new model capabilities, frontend features, and integrations — Scrum's structure would typically be more appropriate. For the QA or DevOps team supporting that product, Kanban might work better.

In practice, many teams use a hybrid — Scrum for development, Kanban-style boards for operations and support."

## SECTION 6: Risk Management, Problem-Solving & Escalation

### Q46. Walk me through how you identify and manage project risks.

**Model Answer:**

"Risk management is something I've applied in both formal and informal contexts.

The process I follow:

**Step 1 — Identify:** I look for risks in three ways. First, at the start of a project, I run a risk brainstorm with the team — 'What could go wrong? What are we uncertain about?' Second, throughout the project, I watch for early warning signals: a dependency that's getting delayed, a team member who seems overloaded, a technical approach that hasn't been proven yet. Third, I check standups specifically for blockers-in-waiting — 'What might slow us down next week?'

**Step 2 — Analyze:** For each risk, I assess two dimensions: probability (how likely?) and impact (how bad if it happens?). High probability + high impact = top priority. I use a simple 3x3 matrix: Low/Medium/High for each.

**Step 3 — Plan a response:** For each significant risk, I want a mitigation plan. Not 'we'll deal with it when it happens' but 'here's how we'll reduce the probability, and here's our contingency if it does happen.'

**Step 4 — Track:** Risks go into a risk register and are reviewed weekly. As the project progresses, some risks realize (become issues), some recede, and new ones emerge.

### Q48. How would you escalate an issue to your manager?

### Q53. How would you prepare and run an effective sprint planning meeting as a PM intern?

### Q54. How do you follow up on action items without seeming pushy?

**Model Answer:**

"This is one of the most nuanced daily skills of a PM coordinator, and I've developed a style that works.

**Document and share immediately.** I send meeting minutes within 24 hours, with the action items table clearly visible. This means my first follow-up isn't a Slack message — it's the minutes I already sent. People often complete action items after seeing them in the minutes.

**If it's blocking something:** I escalate early, with context, as described earlier. The goal is always to move forward, not to assign blame."

## SECTION 9: Documentation, Reporting & Attention to Detail

### Q61. How do you write a status report and what should it contain?

**Model Answer:**

"A status report has one job: give a reader an accurate, actionable picture of project health in under 2 minutes. If it requires 10 minutes to read, it won't be read.

My standard structure:

**Header:** Project name, report date, reporting period, overall RAG status (the single most important signal — a colored label at the top so leadership sees it immediately).

**Executive Summary (2–3 sentences):** What's the overall situation this week? What's the most important thing to know?

**Progress:** What was completed this period? What's currently in progress? What's starting next?

**Milestone Health:** A table showing each upcoming milestone, target date, current status (On Track / At Risk / Delayed), and brief note.

**Risks & Issues:** Current open risks and issues with owner, impact summary, and mitigation action. Not a full risk register — just the top 3–5 active concerns.

**Action Items from Last Report:** Were they completed? If not, updated status.

**Actions Needed from Stakeholders:** If I need a decision or input from leadership, it's explicitly called out here.

**Next Period Focus:** What the team will work on next week.

One principle I follow: the status report should never be a surprise. If there's a 🔴 Red item in the report, the relevant stakeholder should already know about it — the report formalizes it, it doesn't break news."

---

### Q62. Why is documentation important in project management?

**Model Answer:**

"Documentation is undervalued by people who haven't yet experienced what happens without it.

Three specific things documentation prevents:

**1. Decision amnesia.** Projects make dozens of decisions — why was this feature deprioritized? Why did we switch to Transfer Learning? Why is the deadline July 10 and not August 1? Without documentation, these decisions live in people's heads and get lost when someone leaves, goes on leave, or simply forgets. I've seen projects where the same scope decision was re-debated three times because no one had documented the first two.

**2. Requirements misalignment.** When requirements live only in conversations, they mutate as they pass from person to person — like a telephone game. By the time the requirement reaches the engineer, it may be meaningfully different from what the stakeholder intended. Written requirements, reviewed and signed off, prevent this.

**3. Onboarding friction.** When a new team member joins, good documentation means they can get up to speed from documents rather than pulling existing team members into 2-hour onboarding conversations. This protects the team's bandwidth.

At Gagangiri, I built a habit of documenting every decision in a shared Notion space. The payoff came when our stakeholder asked mid-project 'why didn't we include type classification?' — I could point immediately to the requirements document from week 2 where that was explicitly listed as out of scope. No debate, no ambiguity."

---

### Q63. How do you take and distribute effective meeting notes?

**Model Answer:**

"Effective meeting notes are the antidote to 'what did we actually decide in that meeting?' — a question that derails more projects than most PMs admit.

My approach:

**Before the meeting:** Prepare the notes template in advance — date, attendees, agenda items. This forces me to think about what we need to decide, not just discuss, before I walk in.

**During the meeting:** I capture in real time, focusing on three things:
1. **Decisions made** — flagged with a 'DECISION:' label so they're scannable
2. **Action items** — flagged with 'ACTION:' and immediately including owner and due date. Not 'someone will look into this' but 'Ananya will send the updated requirements doc by Friday.'
3. **Open questions / parking lot** — topics raised but not resolved, flagged for follow-up

I don't try to transcribe everything said. I capture what matters: decisions, actions, blockers surfaced.

**After the meeting (within 24 hours):** I clean up the notes and distribute them to all attendees and relevant stakeholders who weren't there. The format is clear, short, and action-first — the action items table appears before the detailed notes because it's what most people need to act on.

I also add these action items to the tracker immediately after distributing — one system of record for all outstanding actions."

**Model Answer:**

"My approach has three phases:

**First — just use it.** I learn tools fastest by doing, not by reading documentation end-to-end. I'll set up a test project in Jira, create a fake sprint, add stories, move them through the board, generate a report. Getting hands dirty in the first hour teaches me more than an hour of reading.

**Second — learn the workflow, not just the features.** A tool like Jira has hundreds of features. I focus on the 20% of features that support 80% of the daily workflow: creating issues, updating status, linking dependencies, monitoring the board, generating sprint reports. Once those are fluent, I add layers.

**Third — ask a specific question when I'm stuck.** I don't ask 'how does Jira work?' I ask 'I'm trying to link two issues so one is dependent on the other — is it the 'linked issues' feature or the 'epic link'?' Specific questions get specific answers and don't waste the expert's time.

I've applied this approach to every tool I've picked up — Notion, Streamlit, PostgreSQL, Postman — and I'm confident I can onboard to any PM tool the team uses within the first week."
