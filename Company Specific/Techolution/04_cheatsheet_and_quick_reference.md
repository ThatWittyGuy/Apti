## 3. The Master Glossary — 80 Terms, One-Liner Definitions

> Know every single one of these cold. These can appear as direct questions or embedded in scenario questions.

### Project Management Core

| Term | Definition |
|------|-----------|
| **Project** | Temporary endeavor with defined start/end to create a unique product or result |
| **Triple Constraint** | Scope, Time, Cost — change one, the others are affected |
| **Milestone** | Significant checkpoint with a date but zero duration (it's a moment, not a task) |
| **Deliverable** | A tangible, verifiable output — a feature, report, or document |
| **Dependency** | Task B cannot start (or finish) until Task A is complete |
| **Blocker** | Something actively preventing progress right now |
| **Scope Creep** | Uncontrolled expansion of scope without adjusting time or cost |
| **Baseline** | The original approved plan — scope, schedule, budget |
| **Change Request** | Formal proposal to modify scope, timeline, or budget |
| **Project Charter** | Document that formally authorizes a project; defines objectives, stakeholders, PM authority |
| **WBS** | Work Breakdown Structure — hierarchical decomposition of all project work |
| **Gantt Chart** | Bar chart showing tasks on Y-axis, timeline on X-axis, with dependencies |
| **Critical Path** | Longest sequence of dependent tasks — determines minimum project duration |
| **Float / Slack** | Extra time a task can be delayed without delaying the project |
| **Action Item** | Specific task with a named owner and due date from a meeting |
| **Status Report** | Periodic project health update — RAG status, milestones, risks, next steps |
| **RAG Status** | Red/Amber/Green — traffic light indicator of project health |
| **RACI Matrix** | Responsible, Accountable, Consulted, Informed — role clarity tool |
| **Stakeholder** | Anyone affected by or having interest in the project |
| **Escalation** | Raising issue/risk to higher authority to resolve it |
| **Risk Register** | Living document tracking all identified risks, owners, and mitigations |
| **Issue Log** | Tracks problems that have already occurred (not uncertain future risks) |
| **KPI** | Key Performance Indicator — measurable value showing progress toward a goal |
| **OKR** | Objectives and Key Results — goal-setting framework (O = qualitative goal, KR = measurable outcomes) |
| **Communication Plan** | Defines who gets what information, how often, through which channel |
| **Lessons Learned** | Post-project documentation of what worked and what didn't for future reference |

### Agile & Scrum

| Term | Definition |
|------|-----------|
| **Agile** | Mindset/philosophy valuing iterative delivery, customer collaboration, and adaptability |
| **Scrum** | Most popular Agile framework — fixed sprints, 3 roles, 3 artifacts, 5 ceremonies |
| **Sprint** | Fixed time-box (1–4 weeks, typically 2) for delivering a defined set of work |
| **Sprint Goal** | A short statement of what the team aims to achieve in a sprint |
| **Product Owner (PO)** | Owns the product backlog; defines WHAT gets built next |
| **Scrum Master (SM)** | Facilitates Scrum; removes blockers; coaches the team — does NOT manage people |
| **Development Team** | Cross-functional, self-organizing group of 3–9 who build the product |
| **Product Backlog** | Prioritized master list of all work for the product — owned by PO, never complete |
| **Sprint Backlog** | Subset of product backlog committed to in the current sprint — owned by dev team |
| **Increment** | Working, potentially shippable product built during a sprint |
| **User Story** | "As a [user], I want [goal] so that [benefit]" — requirement from user's perspective |
| **Acceptance Criteria** | Given/When/Then conditions that define when a story is done |
| **Epic** | Large feature or body of work spanning multiple sprints; contains multiple stories |
| **Story Points** | Relative unit of effort estimation — accounts for complexity, risk, and effort |
| **Velocity** | Average story points completed per sprint — used to forecast |
| **Capacity** | How many story points a team can take on next sprint based on availability |
| **Burndown Chart** | Graph showing remaining sprint work (Y) over time (X) — should trend to zero |
| **Definition of Done (DoD)** | Shared checklist a story must meet before being considered complete |
| **Spike** | Time-boxed investigation task to reduce uncertainty before estimating a story |
| **Technical Debt** | Code or design shortcuts that will need to be fixed later — accumulates over time |
| **Backlog Refinement** | Session to clarify, estimate, and prioritize upcoming backlog items |
| **Sprint Planning** | Ceremony to select and plan sprint work; output = sprint backlog |
| **Daily Stand-up** | 15-min daily sync: what did I do, what will I do, any blockers? |
| **Sprint Review** | End-of-sprint demo to stakeholders; focused on product output |
| **Sprint Retrospective** | End-of-sprint team process reflection; focused on how the team works |
| **WIP Limit** | Maximum tasks allowed in a Kanban column at one time |
| **Kanban** | Visual, flow-based Agile framework with no sprints or prescribed roles |
| **Lead Time** | Total time from request to delivery (Kanban metric) |
| **Cycle Time** | Time from work starting to work completing (Kanban metric) |
| **Velocity Chart** | Sprint-by-sprint graph of completed story points — shows trend over time |

| Term | Definition |
|------|-----------|
| **SDLC** | Software Development Life Cycle — structured phases for planning, building, and deploying software |
| **Frontend** | User-facing UI — what users see and interact with (HTML, CSS, JavaScript, React) |
| **Backend** | Server-side logic, APIs, databases — powers the frontend invisibly |
| **API** | Application Programming Interface — rules for how two systems communicate |
| **REST API** | Most common API type — uses HTTP verbs: GET, POST, PUT, DELETE |
| **Database** | Where data is stored; SQL (structured tables) or NoSQL (flexible documents) |

| **PR / MR** | Pull Request / Merge Request — request to merge code into main branch; requires review |

| **Staging Environment** | Mirror of production used for QA and UAT before release |
| **Production (Prod)** | Live environment — real users use it |

| **Regression Testing** | Ensuring new code changes don't break existing functionality |
| **Unit Testing** | Testing individual code functions in isolation (done by developers) |
| **Integration Testing** | Testing multiple components working together |

### AI/ML Specific

| Term | Definition |
|------|-----------|
| **Machine Learning (ML)** | AI systems that learn patterns from data without explicit programming |
| **Model** | The trained algorithm that makes predictions or decisions |
| **Training Data** | Labeled dataset used to teach the ML model |
| **Model Training** | Process of feeding data through the algorithm to build the model |
| **Inference** | Using a trained model to make predictions on new, unseen data |
| **Accuracy** | % of predictions the model gets correct |
| **Precision** | Of all positive predictions, how many were actually positive |
| **Recall** | Of all actual positives, how many did the model correctly identify |
| **Overfitting** | Model performs well on training data but poorly on new data — too specific |
| **Underfitting** | Model performs poorly even on training data — too simple |
| **Transfer Learning** | Using a pre-trained model and fine-tuning it for a specific new task |
| **CNN** | Convolutional Neural Network — deep learning model for image classification |
| **LLM** | Large Language Model — AI trained on massive text data (GPT, Gemini, Claude) |
| **RAG** | Retrieval-Augmented Generation — grounds LLM responses in real documents |
| **Hallucination** | When an AI confidently generates incorrect or fabricated information |
| **Fine-tuning** | Further training a pre-existing model on domain-specific data |
| **Feature** | An input variable the model uses to make predictions |
| **Labeled Data** | Data with correct answers attached — used for supervised learning |
| **Annotation** | The process of adding labels to training data |
| **Validation Set** | Data held out from training used to evaluate model performance during development |
| **Test Set** | Data held out to evaluate final model performance before deployment |
| **Hyperparameter** | Configuration settings for a model (learning rate, batch size) tuned before training |
| **MLOps** | Practices for deploying and maintaining ML models in production reliably |

## 4. Agile & Scrum at a Glance

### The 5 Ceremonies — Ultra-Compact

```
CEREMONY       WHEN              DURATION   WHO              OUTPUT
─────────────────────────────────────────────────────────────────────
Sprint Plan    Sprint start      4h (2-wk)  Full team        Sprint backlog
Daily Standup  Every day         15 min     Dev team + SM    Blocker list
Sprint Review  Sprint end        2h (2-wk)  Team + stakeholders  Updated backlog
Retrospective  After review      1.5h       Team only        Process action items
Refinement     Mid-sprint        1–2h       PO + dev team    Estimated backlog items
```

### The 3 Questions of Daily Standup
1. What did I **complete** yesterday?
2. What will I **work on** today?
3. Is there anything **blocking** me?

### Sprint Review vs. Retrospective — Never Confuse These
| | Sprint Review | Sprint Retrospective |
|---|---|---|
| **Focus** | The PRODUCT (what was built) | The PROCESS (how we worked) |
| **Audience** | Team + stakeholders | Team only |
| **Output** | Updated product backlog | Process improvement actions |
| **Question** | "Did we build the right thing?" | "Did we work the right way?" |

### Scrum Roles — One-Liner Each
- **Product Owner:** WHAT to build and in what order. Owns the backlog.
- **Scrum Master:** HOW the team works. Facilitates, coaches, removes blockers.
- **Dev Team:** Build the product. Self-organizing. 3–9 people.

### Kanban vs. Scrum — 5 Key Differences
| | Scrum | Kanban |
|---|---|---|
| Time-boxed | Yes (sprints) | No (continuous flow) |
| Ceremonies | 5 defined | Minimal (stand-up optional) |
| Roles | PO, SM, Dev | No prescribed roles |
| Change | Not mid-sprint | Anytime |
| Metric | Velocity | Lead time / Cycle time |

## 5. SDLC Phases — Ultra-Compact Reference

```
PHASE              KEY ACTIVITIES                    OUTPUT
──────────────────────────────────────────────────────────────
1. Requirements    Gather needs, interview            BRD, User Stories, PRD
                   stakeholders, define scope
                   
2. System Design   Architecture, database schema,     HLD, LLD, API contracts,
                   UI wireframes, tech stack choice    DB schema
                   
3. Implementation  Writing code, code reviews,        Working code, PRs merged
                   unit testing by devs               
                   
4. Testing / QA    Integration, system, regression,   QA sign-off, bug list,
                   performance, security, UAT          UAT acceptance
                   
5. Deployment      Release to staging → UAT → prod,   Live product in production
                   smoke testing, go-live              
                   
6. Maintenance     Bug fixes, performance updates,    Patches, new releases
                   monitoring, user feedback loops    
```

**The Rule of Cost of Defects:**
Bug found in Requirements = cheap to fix
Bug found in Design = 3× more expensive
Bug found in Development = 10× more expensive
Bug found in QA = 25× more expensive
Bug found in Production = 100× more expensive
→ **This is why requirements and design are never rushed.**

## 6. PM Frameworks & Models — Cheatsheet

### MoSCoW Prioritization
| Label | Meaning | Example |
|-------|---------|---------|
| **M — Must Have** | Non-negotiable; without it, the product doesn't launch | Login functionality |
| **S — Should Have** | Important but not critical for launch | Google OAuth |
| **C — Could Have** | Nice to have if capacity allows | Biometric login |
| **W — Won't Have** | Out of scope this time; logged for future | QR code login |

### Eisenhower Matrix
```
              URGENT          NOT URGENT
IMPORTANT   | DO NOW          | SCHEDULE
            | (Crises,        | (Planning,
            | deadlines)      | strategy)
────────────┼─────────────────┼──────────────
NOT         | DELEGATE        | ELIMINATE
IMPORTANT   | (Some meetings) | (Busy work)
```

### Risk Probability × Impact Matrix
```
         LOW IMPACT  MEDIUM IMPACT  HIGH IMPACT
HIGH P   | Monitor   |  Mitigate   |  Avoid/Escalate
MEDIUM P | Accept    |  Mitigate   |  Mitigate
LOW P    | Accept    |  Accept     |  Monitor
```

### RACI — The Four Roles
- **R — Responsible:** Does the work. (Can be multiple people)
- **A — Accountable:** Ultimately answerable. Approves. (Only ONE person per task)
- **C — Consulted:** Provides expertise/input. Two-way communication.
- **I — Informed:** Kept updated. One-way communication.

### Stakeholder Power/Interest Grid
```
HIGH POWER │ KEEP SATISFIED  │  MANAGE CLOSELY
           │ (Low engagement) │  (High engagement)
           ├─────────────────┼──────────────────
LOW POWER  │ MONITOR         │  KEEP INFORMED
           │ (Minimal effort) │  (Regular updates)
           └─────────────────┴──────────────────
              LOW INTEREST       HIGH INTEREST
```

### The Triple Constraint — Golden Rule
> "Fast, Good, Cheap — pick two."
- Fast + Good = Expensive
- Fast + Cheap = Low quality
- Good + Cheap = Slow

### OKR Format
```
OBJECTIVE: [Qualitative, inspiring goal]
  KR1: [Measurable outcome 1]
  KR2: [Measurable outcome 2]
  KR3: [Measurable outcome 3]

Example:
O: Make the AI dashboard indispensable for food safety teams
  KR1: Achieve 80%+ model accuracy on water quality detection
  KR2: Dashboard adopted by 100% of production shift supervisors within 30 days
  KR3: Reduce manual water testing time by 60%
```

## 7. Tools Reference Card

### Jira — Key Things to Know
```
HIERARCHY:   Epic → Story → Sub-task
             Epic → Task → Sub-task
             Bug (standalone)

STATUSES:    To Do → In Progress → In Review → Done

KEY FIELDS:  Summary, Assignee, Reporter, Priority,
             Story Points, Sprint, Status, Labels, Components

REPORTS:     Burndown chart, Velocity chart, Sprint report,
             Cumulative flow diagram

AS PM INTERN YOU:
• Create and update issues
• Monitor sprint board daily
• Link dependent issues
• Comment with decisions/blockers
• Generate sprint reports for status updates
• Keep backlog organized and prioritized
```

### Notion — Key Things to Know
```
CORE ELEMENTS:
• Page = document (can contain anything)
• Database = collection of pages with properties
• Property = a field on a database item (date, person, select, etc.)
• View = how you see the database (table, board, calendar, gallery)

PM USE CASES:
• Project overview page (single source of truth)
• Requirements database (filterable, searchable)
• Milestone tracker (table view with status properties)
• Meeting notes wiki (one page per meeting)
• Risk register (database with probability/impact properties)
• Sprint documentation and retrospective notes
```

### Trello — Key Things to Know
```
STRUCTURE:
• Board → Lists (columns) → Cards (tasks)

FEATURES TO KNOW:
• Labels: color-coded tags (Red = urgent, Blue = frontend)
• Checklists: sub-tasks within a card
• Due Dates: deadlines shown in calendar view
• Power-Ups: integrations (Slack notifications, calendar view)

BEST FOR: Simple projects, small teams, visual Kanban workflows
LIMITATION: No native Agile reporting (no burndown, no velocity)
```

### Slack — Best Practices
```
DO:
✓ Use channels per project/workstream
✓ Use threads to keep channels clean
✓ Tag specific people for urgent items
✓ Document decisions beyond Slack (in Notion/Jira)
✓ Format action items clearly: @Name — Action by [Date]: [Task]

DON'T:
✗ Make important decisions only in Slack (they get lost)
✗ Message someone and then follow up in 10 minutes (respect async)
✗ Use one general channel for everything
✗ Expect instant responses from engineers (they're in deep work)
```

## 8. Technical Concepts — Plain English Cheatsheet

### The Three Layers of Any Web App
```
┌─────────────────────────────────┐
│   FRONTEND (React, HTML, CSS)   │  ← What users see
│   User Interface, Forms, Clicks  │
├─────────────────────────────────┤
│   BACKEND (Node.js, Express,    │  ← Business logic
│   Python, Java)                 │     Processing, rules
│   APIs, Authentication, Logic   │
├─────────────────────────────────┤
│   DATABASE (PostgreSQL,MongoDB) │  ← Where data lives
│   Users, Products, Orders, Logs │
└─────────────────────────────────┘
```

### API — The Restaurant Analogy
- **You (Frontend)** = the customer
- **Menu (API)** = the defined options you can request
- **Kitchen (Backend)** = processes your order
- **Food (Response)** = what you get back

GET = "Give me the user's profile"
POST = "Create a new user account"
PUT/PATCH = "Update this user's email"
DELETE = "Delete this account"

### Environments — The Three-Stage Pipeline
```
DEV → STAGING → PRODUCTION
(build)  (test)    (real users)
```
- Dev: Developers write and test locally
- Staging: QA team tests; mirrors production
- Production: Live — real users — treat with extreme care

### When Engineers Say... (PM Translation)
| Engineer Says | What It Means for PM |
|--------------|---------------------|
| "The API isn't ready yet" | Frontend team is blocked — dependency risk |
| "We need to refactor this" | Technical debt being paid — expect slower velocity |
| "It's in code review" | Work is done but waiting on another person — may be bottleneck |
| "Blocked by the database migration" | Can't proceed until schema change is complete |
| "The CI is broken" | Nobody can deploy anything until this is fixed — high urgency |
| "We need a spike for this story" | Too uncertain to estimate — need investigation time first |
| "This will cause a breaking change" | Other systems may stop working — need coordination |
| "Technical debt" | Shortcuts taken earlier that now slow things down |
| "We're in feature freeze" | No new features — only bug fixes before launch |
| "We need to write tests for this" | Time for quality assurance work — don't skip this |

## 9. AI/ML PM Concepts — Quick Reference

### AI Project vs. Traditional Software Project — Key Differences
| | Traditional Software | AI/ML Project |
|---|---|---|
| **Output certainty** | Deterministic (same input = same output) | Probabilistic (outputs vary) |
| **"Done" definition** | Feature works as specified | Model meets accuracy threshold |
| **Key dependency** | API, design, other code | Training data quality and quantity |
| **Timeline predictability** | High | Low (experimentation is inherent) |
| **QA** | Standard functional testing | Model evaluation + conversation quality review |
| **Main risk** | Requirements misalignment | Data quality, accuracy plateau |

### The AI Development Cycle
```
Data Collection → Data Labeling/Annotation → Model Training → 
Model Evaluation → Iteration → Deployment → Monitoring
```
Each cycle can take days to weeks. Multiple cycles are normal.

### Key AI Metrics a PM Should Track
| Metric | What It Means | Why PM Cares |
|--------|--------------|-------------|
| **Accuracy** | % of predictions correct | Primary success metric for classification |
| **Precision** | Of positive predictions, % actually positive | Matters when false positives are costly |
| **Recall** | Of actual positives, % correctly found | Matters when false negatives are costly |
| **Latency** | Time for model to return a prediction | Affects user experience; tracked post-launch |
| **Throughput** | Requests the model can handle per second | Affects scalability; needs load testing |
| **Drift** | Model accuracy degrading over time | Requires model retraining — tracked in maintenance |

### Data Dependencies — The PM's Biggest AI Risk
```
No Data → No Training → No Model → No Feature → No Launch

Mitigation strategies:
1. Identify data sources in week 1 of planning
2. Build data collection as a first-class sprint workstream
3. Track data availability weekly (it's on the critical path)
4. Build mock/synthetic data plan as contingency
5. Consider Transfer Learning if proprietary data is limited
```

### Communicating AI Uncertainty to Stakeholders
**DON'T say:** "The model will be ready by June 15."
**DO say:** "Our target accuracy is 85%. Based on current progress at 73% with 2 iterations complete, we estimate reaching target in 3–4 more weeks, putting us at approximately mid-June. I'll update this weekly as we have more data."

**DON'T say:** "The AI will always give the right answer."
**DO say:** "The model achieves 80.9% accuracy on our test set, which means approximately 1 in 5 predictions may need human review. We've built an escalation flow for low-confidence outputs."

## 10. Risk Management — One-Page Reference

### Risk vs. Issue
```
RISK = Might happen (uncertain, future) → Manage proactively
ISSUE = Has happened (certain, present) → Resolve now
```

### Risk Response Strategies
| Strategy | When to Use | Example |
|----------|-------------|---------|
| **Avoid** | Risk is too high to accept | Don't use unstable 3rd-party API — build internally |
| **Mitigate** | Reduce probability or impact | Add buffer time; cross-train team members |
| **Transfer** | Shift risk to another party | Vendor SLA; insurance |
| **Accept** | Low risk, not worth the mitigation cost | Minor UI inconsistency in v1 |

### Risk Register — Required Columns
```
ID | Description | Probability (H/M/L) | Impact (H/M/L) | 
Score | Owner | Mitigation Plan | Contingency | Status
```

### When to Escalate a Risk
Escalate immediately when:
- Risk probability × impact = HIGH
- Risk is on the critical path
- You've tried to mitigate and can't
- It requires resources or authority above your level
- A milestone or stakeholder commitment is threatened

### Escalation Message Structure
```
WHAT: [Specific risk/issue in 1–2 sentences]
IMPACT: [Effect on timeline/scope/budget if unresolved]
TRIED: [What you've already done]
OPTIONS: [2–3 possible responses]
RECOMMENDATION: [What you think should happen]
NEEDED BY: [Specific date for a decision]
```

## 11. Budget Tracking — Core Concepts

### Budget Terminology
| Term | Definition |
|------|-----------|
| **Approved Budget** | Total sanctioned spend for the project |
| **Committed Spend** | Contracted/obligated money (even if not yet invoiced) |
| **Actual Spend** | Money already paid/invoiced |
| **Remaining Budget** | Approved minus Committed (NOT Approved minus Actual) |
| **Burn Rate** | Rate at which budget is being consumed per period |
| **Budget Variance** | Actual vs. planned spend — positive = underspent, negative = overspent |
| **Cost to Complete** | Estimated remaining spend to finish the project |
| **EAC** | Estimate at Completion — projected total cost at current burn rate |

### Budget Health Check Formula
```
If (% Budget Consumed) > (% Project Complete) → At Risk 🟡
If (% Budget Consumed) > (% Project Complete + 15%) → Critical 🔴
If (% Budget Consumed) ≈ (% Project Complete) → Healthy 🟢
```

### AI Project-Specific Budget Risks
- **LLM API costs:** Usage-based; can scale exponentially as traffic grows
- **GPU/Compute costs:** Model training can be expensive; track cloud costs weekly
- **Data annotation costs:** Labeling large datasets has per-item costs
- **Retraining costs:** Each model iteration has compute costs

### Budget Red Flags to Escalate Immediately
- Any category exceeding 100% of allocated budget
- Overall project exceeding 80% budget before 80% completion
- Sudden spike in cloud/compute costs without corresponding milestone progress
- Vendor invoice arriving that was not planned (unbudgeted spend)

## 14. Stakeholder Communication — Quick Rules

### The 5 Golden Rules of PM Communication
1. **Be specific, not vague.** "Delayed by 5 days because of QA environment downtime" not "there are some issues."
2. **Lead with impact, not cause.** "The beta launch is at risk" before "here's the technical reason why."
3. **Never surprise a stakeholder.** If it's going in the status report as Red, they should already know.
4. **Action-oriented updates.** Every bad news item needs an action item attached to it.
5. **Match the channel to the urgency.** Critical blocker = phone call. Weekly update = email/report.

### Adjusting Communication by Audience
| Audience | What They Care About | How to Communicate |
|----------|---------------------|-------------------|
| **Leadership/VP** | Business outcomes, milestone health, decisions needed | High-level RAG status, 1-page report, no jargon |
| **Product Manager** | Feature progress, risks to sprint goals, scope changes | Weekly sync, status report, Jira updates |
| **Engineering Team** | Clear requirements, blockers removed, priorities | Jira, Slack, daily standup |
| **Design Team** | Feedback turnaround time, design review schedule | Figma comments, weekly design reviews |
| **QA Team** | Test scope, acceptance criteria, release dates | Test plans, bug triage meetings |
| **External Stakeholders** | Delivery timeline, major milestones, demo schedule | Formal email updates, demos |

### The "So What?" Test for Every Update
Before sending anything, ask: "So what?" 
- Bad: "The team completed 8 stories this sprint."
- Good: "The team completed 8 of 10 sprint stories. The 2 remaining are carrying into Sprint 8. This keeps us on track for the July 1 beta launch."
